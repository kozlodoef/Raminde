# Российская оплата Raminde

Серверный адаптер ЮKassa и месячный счётчик. Google Play Billing не используется. Провайдера можно заменить отдельным адаптером банка, сохранив API клиента.

**Не развёрнут и не подключён к реальному магазину.** Без merchant credentials и цен платёжные операции отвергаются. Карточные данные приложение/этот сервер не принимают: пользователь открывает HTTPS-страницу провайдера. СБП/карты зависят от методов, подключённых в договоре с провайдером.

## Запуск

Node.js 24+, без сторонних серверных зависимостей (используется node:sqlite):

```sh
cp .env.example .env
# заполнить .env на сервере, не в репозитории
npm start
npm test
```

Сервер слушает loopback:8080. Перед ним нужен HTTPS reverse proxy, ограничения запросов, мониторинг, резервные копии SQLite, управление секретами и восстановление после сбоя. Разместить данные в соответствии с применимыми требованиями законодательства, включая обработку персональных данных. Открытый HTTP endpoint для мобильного релиза не допускается.

Во фронтенде установить `VITE_BILLING_API=https://ваш-домен` и пересобрать APK. В клиент **не передаются** shopId и secret. Настроить webhook `/api/webhook` для `payment.succeeded` и `refund.succeeded`, а RETURN_URL — на собственную информационную HTTPS-страницу. RETURN_URL не активирует доступ: сервер повторно читает статус платежа через merchant API.

## Поведение

- 10 новых правил в календарный месяц; срабатывания не расходуют квоту.
- Резервирование/подтверждение квоты идемпотентно по идентификатору правила.
- Месячный и годовой доступ, цены — серверная конфигурация, а не выдуманные цены клиента.
- **Предоплата без автоматического списания.** Рекуррентное автопродление требует отдельного согласия и доработки; карточные токены сейчас не сохраняются.
- Подтверждённый успешный платёж продлевает доступ один раз; поддельный webhook не даёт подписку.
- Подтверждённый полный возврат пересчитывает права по оставшимся оплаченным счетам; частичные возвраты требуют отдельной согласованной политики.
- Отмена/истечение доступа не отключает локальные сохранённые напоминания.
- Покупки и счётчик восстанавливаются ключом прежней сессии. Ключ — секрет, хранить в менеджере паролей. На Android он хранится зашифрованным с Android Keystore. Веб-демо использует localStorage; это не эталон защищённого хранения коммерческого веб-клиента.

## Перед реальными продажами

1. Выбрать провайдера, заключить договор, настроить магазин и фискализацию. Проверить RECEIPTS/VAT_CODE/TAX_SYSTEM_CODE с бухгалтером; не угадывать налоговые параметры.
2. Утвердить цены, оферту, политику конфиденциальности, условия возврата и канал распространения приложения.
3. Развернуть собственный сервер и провести тестовые платежи/возвраты в sandbox, затем контрольный реальный платёж с согласия владельца.
4. Заменить/дополнить анонимную сессию устойчивой идентификацией аккаунта. Сейчас создание новой анонимной сессии или удаление данных позволяет получить другую бесплатную квоту; локальную защиту от переустановки гарантировать нельзя. **Не запускать коммерческий антифрод на одном анонимном идентификаторе.**
5. Утвердить офлайн-политику. В текущей версии с настроенным API создание нового напоминания требует связи для резервирования квоты. Уже сохранённые события работают офлайн. Долгосрочный кэш premium/офлайн-бюджет ещё не реализован.
6. Добавить поддержку кассовых ошибок, частичных возвратов, кабинета поддержки, более строгие distributed rate limits/CSRF-policy при смене модели авторизации и мониторинг webhook failures. Текущий in-process rate limiter — только базовая защита одного процесса.

Без этих шагов сервер — тестируемая основа интеграции, не готовый коммерческий платёжный продукт.
