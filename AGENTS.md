# Инструкции для агентов: проект «Remind me» (Raminde)

Android-приложение голосовых напоминаний: React/Capacitor-интерфейс и собственный
нативный движок SQLite → AlarmManager → TextToSpeech/TTS-service.

Этот файл — правила работы **внутри этого репозитория**. Глобальные инструкции
пользователя (`~/.dsh/AGENTS.md`) остаются в силе; при конфликте приоритет у
прямого указания пользователя, затем у этого файла, затем у глобального.

**Пользователь — не программист.** Веди работу так, чтобы результат можно было
проверить, не читая код. Подробности — в разделах «Процесс работы» и
«Экономия контекста» ниже.

## Git

- `git` доступен из PATH (Git for Windows, `C:\Program Files\Git\cmd`,
  версия 2.56.1). Полные пути к `git.exe` не использовать, `GIT_EXE` не нужен.
  Системный PATH не менять, ПО не устанавливать самостоятельно.
- Репозиторий инициализирован; основная ветка `main`.
  `tools/git-history.mjs` — резервный способ, если git недоступен; читает
  `refs/heads/master` и на ветке `main` может падать с ENOENT.
- Коммит после каждой успешной сборки/тестов и перед любым крупным
  изменением. Сообщения — на русском, понятные пользователю.
- Если 2–3 попытки починить сборку не удались — остановиться, описать
  вероятную причину и предложить откат к последнему рабочему коммиту
  (`git reset --hard <hash>` / `git checkout <hash> -- .`), объяснив,
  что именно откатится.
- Никогда не коммитить и не добавлять в индекс: `node_modules/`, `dist/`,
  `build/`, `.gradle/`, `.gradle-home/`, `tmp-*`, `*.log`. Они закрыты
  `.gitignore`; если что-то из этого появилось в `git status` — не
  «добавить на всякий случай», а разобраться, почему `.gitignore` не сработал.
- Концы строк зафиксированы в `.gitattributes` (`eol=lf` для всех текстовых
  файлов). Не менять `.gitattributes` и не запускать `git config core.autocrlf`
  без явной просьбы: CRLF ломает разбор `hotwords.txt` и sherpa-onnx.

## Ограничения среды
- Установку ПО, правку системного PATH и переменных среды выполняет
  пользователь. Агент эти настройки не меняет; если нужно — просит.
- Android-инструменты по умолчанию пишут в профиль пользователя. При сборке
  задавать `ANDROID_USER_HOME`, `GRADLE_USER_HOME`, `TEMP`/`TMP` внутри рабочей
  папки, иначе падают загрузка манифестов, поиск пакетов и компилятор Kotlin.
- Лицензии SDK принимаются повторно после смены `ANDROID_USER_HOME`:
  `tools/android-env.ps1`, затем `sdkmanager --licenses`.

## Кодировки и текст

- Исходники и документация — **UTF-8 без BOM**, переводы строк LF. BOM ломает
  разбор (в частности, sherpa-onnx спотыкается на первой строке `hotwords.txt`).
- Вся документация проекта — на русском языке; новые документы и комментарии
  писать по-русски, сохраняя уже принятую терминологию.
- Пользовательские фразы и тексты полей — русские; времена в интерфейсе
  показываются в 24-часовом формате.
- Многострочные PowerShell/Node-скрипты лучше держать в файлах: вывод кириллицы
  через конвейер в консоли может искажаться.

## Что нельзя ломать

- **Микрофон никогда не включается автоматически**, в том числе после обновления
  со старой настройкой `autoListen`. Старт — только по «Начать».
- Сохранённые напоминания, группы, цвета и настройки должны переживать обновление
  APK; прежняя несохранённая очередь архивируется локально и не превращается в
  напоминания без подтверждения.
- Лимит — **12 срабатываний в выбранную дату**; 13-е отклоняется с видимой
  ошибкой и без ложного успеха.
- Цвет новой группы не перекрашивает сохранённые события; цвет не единственное
  различие карточек (есть текст и время).
- Сохранение подтверждается только после реального планирования; сообщения об
  ошибке не очищают введённый текст.
- Не считать выполненным то, что не проверено на реальном телефоне: фон, Doze,
  блокировка, перезагрузка, OEM-ограничения, TalkBack и крупный шрифт —
  зона ручной приёмки, а не unit-тестов.

- Данные пользователя (имя, текст, расписания) хранятся локально; не отправлять

## Процесс работы

- **Перед любым изменением кода — план из 3–7 пунктов простыми словами.
  Дождаться «ок» пользователя. Только потом менять код.**
- Маленькие шаги: одно проверяемое изменение → сборка/тесты → отчёт.
  Не смешивать несколько крупных правок в одном шаге.
- В конце шага — два блока:
  - **«Что я сделал»** — 3 пункта, без кода;
  - **«Что тебе проверить»** — что нажать / что запустить / что скопировать
    при ошибке.
- Без явного «ок» не делать: переписывание архитектуры, обновление версий
  Gradle/AGP/Kotlin/зависимостей, массовые переименования/перемещения файлов,
  добавление библиотек, удаление постороннего кода.
- Если не уверен в причине ошибки — сказать «не уверен» и предложить, как
  проверить. Не править наугад.
- После каждого завершённого этапа обновлять `voice-reminder/PROJECT-STATUS.md`
  кратко: что работает, что сломано, какие файлы менялись, версии, что дальше.
  Этот файл — вход в новый чат.

## Экономия контекста

- Не выводить файлы целиком — только изменённые строки и краткое описание
  остального.
- Из логов Gradle — первые ~30 строк ошибки и блок `Caused by` /
  `What went wrong`; полный лог сохранять в файл и смотреть хвост.
- Не пересказывать историю диалога и не повторять ранее показанный код.
- Не читать файлы, не относящиеся к задаче; искать точечно (grep/поиск),
  а не «прочитай весь проект».
- При старте нового чата — запросить `PROJECT-STATUS.md` и текст ошибки,
  не просить всю историю.

## Стиль работы над кодом

- Правка логики разбора/календаря сопровождается регрессионным тестом, а не
  подгонкой ожиданий под текущий ошибочный результат.
- Две реализации календаря (JavaScript и Java) должны оставаться согласованными:
  изменение одной требует проверки второй.
- Заметки о версии и приёмке добавлять в `voice-reminder/PROJECT-STATUS.md` и
  `voice-reminder/RELEASE-CHECKLIST.md`, краткое описание — в `README.md`.
- `USE_HOTWORDS` в `VoskRecognitionPlugin.java` остаётся `false`: замер показал,
  что подсказка ухудшает WER на текущей модели. Включать только после появления
  модели с BPE-словарём и повторного замера `tools/measure-hotwords.py`.
- Не объявлять готовым к продаже то, что перечислено в разделе «Остаётся до
  коммерческого релиза»: реальный эквайринг, устойчивые аккаунты, release-подпись,
  политика приватности и канал доставки APK.
